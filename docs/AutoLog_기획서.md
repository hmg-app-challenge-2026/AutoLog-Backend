## 0. 한 페이지 요약

업무용 승용차는 세법상 운행기록부가 있어야 차량비를 비용으로 인정받는다. 그래서 수많은 법인과 개인사업자가 매달 운행기록을 손으로 쓰거나, 스마트폰 GPS 앱·블루투스 비콘 같은 **차량 바깥의 장치**로 기록한다. 이 방식은 폰을 두고 내리면 기록이 끊기고, GPS 오차로 계기판과 거리가 어긋나며, 주유 영수증은 또 따로 모아야 한다.

**AutoLog는 기록 주체를 차량 자체로 옮긴다.** Pleos Connect 위에서 Vehicle SDK로 계기판 누적 주행거리를 읽고, NaviHelper로 목적지를 받아, 운행이 끝나면 운행기록 초안이 이미 만들어져 있다. 운전자는 정차 후 "거래처 방문" 한 번만 승인하면 되고, 주유 영수증은 찍으면 그 운행에 자동으로 붙는다. 월말에 관리자는 예외 몇 건만 확인하고 국세청 양식 운행기록부를 내려받는다.

| 심사 기준 | AutoLog의 답 |
|---|---|
| **차량특화성** | 주행거리의 출처가 스마트폰이 아니라 차량 계기판. 외부 장치·폰 없이 차량 자체가 기록. 정차 상태에서만 확인 UI 노출 |
| **창의성** | 기존 서비스가 "폰으로 기록"하던 것을 "차가 기록"으로 전환. 운행과 지출 증빙을 하나의 기록 체계로 연결. 자동화 결과에 출처·신뢰도·승인 이력을 남기는 증빙 중심 설계 |
| **기술 활용성** | Vehicle SDK Odometer가 거리, NaviHelper가 목적지, Fused Location이 출발·도착 좌표, SpeechToText가 목적 음성 입력을 담당. 핵심 흐름은 Odometer + NaviHelper 두 개만으로 완성되도록 설계해, 나머지는 더하면 좋아지고 빠져도 멈추지 않는 구조 |
| **사업성** | 명확한 B2B 초기 고객 + 개인사업자 확장. 월말 장부 마감이라는 강제 재방문 주기. 차량당 월 구독 SaaS. 리스 잔여거리·가족 공용차 등 B2C 확장 로드맵. **운행 원본이 차 안에 있어 서버 없이도 개인사업자는 완결** |

## 1. 문제 정의

### 1.1 누가, 무엇 때문에 불편한가

| 사용자 | Pain Point |
|---|---|
| 법인차 운전 직원 | 출발·도착·거리·목적을 매번 기억해 입력. 영수증 보관 후 재입력. 월말 독촉 |
| 차량·회계 관리자 | 누락 기록 추적, 영수증 취합, 세무 양식으로 재가공. 직원별 기록 신뢰도 검증 불가. **운행·출장 일정·영수증이 따로 놀아 누락·중복·불일치를 사람이 대조** |
| 공용 법인차 조직 | 여러 직원이 한 차를 쓰면 **누가, 어떤 목적으로, 어느 비용을** 썼는지 사후 귀속이 어려움 |
| 개인사업자 | 운행기록부 없으면 차량비 공제 제한. 그러나 혼자 꾸준히 쓰기 어려움 |

문제의 핵심은 "기록"이 아니라 **"검증·정산"에 남아 있는 수작업**이다. 기존 서비스가 기록 자동화는 상당히 해결했지만, 운행·업무 일정·증빙 세 가지를 맞춰보는 일은 여전히 사람이 한다.

### 1.2 기존 해법의 한계

| 방식 | 한계 |
|---|---|
| 수기·엑셀 | 누락, 기억 의존, 사후 작성으로 신뢰도 낮음 |
| 스마트폰 GPS 앱 | 폰을 두고 내리면 기록 없음. 터널·지하·도심 음영에서 거리 오차. 배터리 소모. 운전자가 아닌 폰 소지자를 기록 |
| 블루투스 비콘·OBD 장치 | 장치 구매·장착·관리 비용. 차량 교체 시 재설치 |
| 클라우드 플릿 관제 | 대형 플릿·관리자 중심. 운전자 UX와 국내 세무 양식·영수증 연결 부재 |

공통점은 **차량이 이미 알고 있는 값(계기판 거리, 내비 목적지)을 차량 밖에서 다시 추정한다**는 것이다.

## 2. 솔루션 개요

### 2.1 핵심 아이디어

```
기존:  차량 → (스마트폰 GPS / 비콘이 추정) → 운행일지 앱 → 사람이 영수증 별도 입력
AutoLog: 차량 계기판·내비 → Pleos Connect 앱이 직접 기록 → 영수증이 운행에 자동 연결 → 장부 완성
```

### 2.2 세 가지 설계 원칙

1. **Vehicle-Native Logging** — 거리는 차량 누적 주행거리계, 목적지는 내비게이션. 추정하지 않고 읽는다.
2. **Trip-to-Expense Linking** — 운행 기록과 지출 증빙을 하나의 체계로 묶는다. 운행일지와 주유비 장부를 따로 쓰지 않는다.
3. **Evidence-Aware Automation** — 자동 수집한 값과 사용자가 승인한 값을 구분해 저장한다. 출처·신뢰도·수정 이력이 남는다. 세무 데이터는 "자동으로 틀리는 것"이 "수동으로 느린 것"보다 위험하기 때문이다.
4. **3원 데이터 자동 대조** — [차량 운행 원장] · [출장·배차 등 업무 기록] · [영수증·비용 증빙] 세 축을 교차 검증한다. 운행과 일정은 맞는데 증빙이 없으면 비용만 미확정으로 두고, 증빙은 있는데 그 시간대 운행이 없으면 검토 대상으로 올린다. **불일치를 부정 사용으로 단정하지 않는다** — 관리자가 볼 항목을 골라주는 것이 목적이다.

### 2.3 자동 수집과 목적 판단의 분리

차량은 **언제, 어디까지, 얼마나** 달렸는지 측정할 수 있다. 그러나 그 운행이 **업무였는지**는 데이터만으로 확정할 수 없다. AutoLog는 주행·지출 사실은 자동 기록하되, 업무 목적은 추천하고 사용자가 승인하는 구조를 따른다.

### 3.1 AutoTrip — 주행 자동 기록

**거리 계산**

```
운행거리 = 도착 시 누적주행거리(Odometer) − 출발 시 누적주행거리(Odometer)
```

GPS 궤적 적분이 아니라 차량 계기판 값을 쓴다. 내비·위치는 **어디로**, 계기판은 **얼마나**를 담당한다.

**기록 데이터**

| 데이터 | 출처 |
|---|---|
| 차량 식별자 | 초기 등록 + Vehicle SDK 차량 정보 |
| 운전자 | 앱 진입 시 **사용자 선택**(넷플릭스식 프로필) → 없으면 배차·배정으로 서버가 역추론 → 그래도 없으면 미확정 |
| 출발·도착 시각 | 세션 이벤트 타임스탬프 |
| 출발·도착 누적거리 | Vehicle SDK Odometer |
| 목적지 | NaviHelper `getDestinationInfo()` |
| 출발·도착 좌표 | Fused Location SDK (차량 GPS·IMU·카메라 융합 위치) → 등록 장소 매칭 |
| 출발지 라벨 | 좌표의 등록 장소 매칭 / 직전 운행 도착지 / 사용자 선택 |
| 업무 목적 | SmartPurpose 추천 → 사용자 승인 |

**운행 세션 상태**

```
IDLE → RECORDING → STOP_CANDIDATE ─(짧은 정차 후 재출발)→ RECORDING
                        └─(종료 조건)→ FINALIZING → PENDING_REVIEW → CONFIRMED
                                              └─(데이터 누락)→ NEEDS_RECOVERY
```

**주행 중에는 운전자가 내비를 본다.** 운행 시작 후 앱은 Foreground Service로 뒤에서 기록하고, 주행 중 정보는 지속 알림으로만 보여준다. 운전자가 앱 화면을 볼 일은 출발 전과 정차 후뿐이다.

**시동이 꺼져도, 앱을 안 열어도 거리는 남는다.** 주행 중 10초마다, 기어 P 전환 시 즉시 계기판 값을 저장한다. 시동 OFF 알림은 받지 못한다고 가정하고, 다음 시동 때 계기판 값으로 종료를 확정한다. 앱을 열지 않고 운행한 경우에도 마지막 저장값과 현재 계기판의 차이가 1 km 이상이면 "기록되지 않은 운행 N km"를 제안한다 — 계기판은 앱이 꺼져 있어도 돌기 때문에 가능하며, 폰 GPS 앱은 꺼진 구간을 복구할 수 없다.

Trip(연속 이동) / Stop(정차·방문) / Journey(같은 업무 목적의 Trip 묶음)를 분리해, "본사 → 주유소 → 거래처" 같은 경로에서 주유소 경유가 목적 분류를 흔들지 않게 한다.

**2단계 구현**

- 기본: 앱이 운행 시작·종료를 관리하고 실제 차량 Odometer를 읽어 기록 생성 → **반드시 구현**
- 완전 자동: 차량 상태 이벤트·백그라운드 실행이 검증되면 세션 자동 시작·종료 → 지원 시 적용

### 3.2 SmartPurpose — 업무 목적 추천

| 대분류 | 세부 |
|---|---|
| 일반 업무용 | 거래처 방문, 외근, 출장, 회의, 지점 이동 |
| 출퇴근용 | 출근, 퇴근 |
| 비업무용 | 개인 이동 |
| 미확정 | 근거 부족, 확인 필요 |

국세청 운행기록부의 출퇴근용·일반 업무용 구분에 맞춘다.

**규칙 기반 추천 (MVP)** — 입력 신호: 등록 장소(본사·지점·거래처), 내비 목적지, Fused Location 출발·도착 좌표, 직전 출발지, 요일·시각, 동일 장소의 과거 승인 분류, **배차 예약·일정**(운전자가 폰에서 예약, 관리자가 운영 웹·CSV로 등록).

| 관측 | 추천 |
|---|---|
| 자택 → 회사 | 출근 |
| 등록된 출장·방문 일정과 시각·목적지 일치 | 해당 일정의 목적(최고 확신도) |
| 회사 → 등록 거래처 | 거래처 방문 |
| 본사 → 지사 | 사업장 이동 |
| 회사 → 미등록 장소 | 확인 필요 |
| 과거 업무 승인 장소 재방문 | 기존 목적 재추천 |

장소 일치만으로 업무를 확정하지 않는다. 확신도가 낮으면 반드시 사용자에게 묻는다. 학습 기반 추천은 확장 단계에서 검토한다.

### 3.3 AutoExpense — 주유·비용 자동 정산

결제 사실 / 주유 사실 / 차량 연결을 구분해 처리한다. 입구는 두 개다.

| 입구 | 흐름 | 언제 |
|---|---|---|
| **음성·탭(즉시)** | 연료 센서 급증 + 주유소 정차 감지 → "주유하셨나요?" → "6만8천원 40리터" 한마디 → 현재 운행의 정차에 연결 | 주유 직후, 차 안에서 |
| **영수증 OCR(사후)** | 정차 중 [영수증 저장] → QR → 폰 카메라 페이지 → 촬영 → 중계 서버가 **Gemini**로 추출 → 차 앞으로 전달 → 차 화면에서 확인·운행 연결 | 폰이 있을 때, 15초 |

```
폰 촬영 → 중계 서버(Gemini OCR: 거래일시·상호·유종·수량·단가·금액·카드 뒷4) → 검산(수량×단가 vs 금액, 할인 분리)
→ 차량 inbox → 차 앱이 정차 시 수신 → 운행·정차 매칭(촬영 시각, 주유소 정차, 중복 해시) → 운전자 1탭 확정 → 차 Room
```

| OCR 신뢰도 | 기준(초기 목표) | 처리 |
|---|---|---|
| 높음 | 필수 필드 95%↑ + 검산 통과 | [확정] 1탭 |
| 중간 | 75~95% 또는 일부 불일치 | 차 화면에서 수정(탭·음성) |
| 낮음 | 75%↓ 또는 핵심 필드 누락 | 재촬영·수동 입력 |

영수증 사진은 서버에 30일만 보관하고, 카드번호는 뒷 4자리만 남긴다. 음성 건과 OCR 건이 같은 시각이면 병합한다. 법인카드 API는 제휴 이후 확장 기능이다.

### 3.4 TaxLedger — 운행기록부·비용 장부

국세청 「업무용승용차 운행기록 방법에 관한 고시」 양식 기준으로 생성한다.

- 업무용승용차 운행기록부(XLSX)
- 차량별 월간 주유·유지비 내역
- 차량별 업무사용비율 요약
- **3원 대조 검토 리포트** — 운행거리 누락, 목적 미확정, 일정은 있는데 운행 없음, 운행은 있는데 증빙 없음, 중복 영수증, 주유량 대비 주행거리 비정상(예: 월 300 km에 200 L) 등 관리자가 볼 항목만 모은 목록

```
총 주행거리 = 출퇴근 + 일반업무 + 비업무 + 미확정
업무사용비율 = (출퇴근 + 일반업무) / 총 주행거리 × 100
```

미확정 거리는 업무용에 임의 포함하지 않는다. 운행기록부와 비용 장부는 별도 생성한다(주유비가 많다고 업무 거리가 늘지 않는다). 수정 시 원본 차량 데이터는 보존하고 수정값·사유·수정자를 별도 기록한다.

### 3.5 운전자 식별 — 공용 법인차의 "누가"

헤드유닛 앱은 운전자가 누구인지 모른다. 폰 앱의 "폰 주인 = 운전자" 가정이 없기 때문에, 신호를 겹쳐 쓰고 확신이 없으면 미확정으로 남긴다.

| 순위 | 신호 | 확신도 | 비고 |
|---|---|---|---|
| ① | 앱 진입 시 **사용자 선택** — 최근 사용자 3명 카드 + 검색, 넷플릭스 프로필 방식 | 1.0 | 1탭. 폰·비콘·QR 불필요 |
| ② | **배차 예약** — 이 차·이 시간대에 예약한 운전자 | 0.95 | 운전자가 폰에서 예약, 관리자가 등록. 공용차는 어차피 배차표가 있다 |
| ③ | 차량 배정 | 0.85 | 관리자 등록 |
| ④ | 일정 역추론 — 이 시각 이 목적지에 일정이 있는 사람이 1명 | 0.80 | 후보로만 제시 |
| ⑤ | 직전 운행 운전자 | 0.60 | 후보로만 제시 |

미확정 운행은 운전자가 폰에서 "내 운행 가져가기"로, 관리자가 운영 웹에서 배정으로 사후 확정한다. 확정되지 않은 운행은 운행기록부에 성명 공란·업무거리 0으로 집계하고 "검토" 열에 표시한다. 카택스류 폰 앱이 공용차에서 남의 이름으로 기록되거나 폰 없는 운전자를 놓치는 문제를, 차가 기록하고 사람은 1탭으로 붙이는 구조로 푼다.

### 3.6 차가 만드는 엑셀, 우체통 역할의 서버

**원칙: 운행 기록의 원본은 차량 안(Room)이다. 서버는 폰·관리자가 차에 넣어주는 것만 중계하는 우체통이고, 엑셀·메일은 차가 직접 만든다.**

| 차량 앱(운전자) | 폰(운전자) | 운영 웹(관리자) | 중계 서버 | 회계(메일) |
|---|---|---|---|---|
| 사용자 선택, 운행 시작·종료, 목적 확인, 주유 음성 입력, 영수증 확인, 거래처 등록, **엑셀 생성·메일 발송** | QR 찍고 영수증 촬영 | 차량·연결 코드, 직원, 장소, 배차, 수신자 등록 | 영수증 → Gemini OCR → 차 앞으로 / 직원·장소·배차·수신자 → 조직 차량 앞으로 | 차량별 운행기록부 수신 — "검토" 열 → 운전자에게 확인 요청 |

차가 월말(또는 정차 중 탭 2번)에 국세청 양식 운행기록부를 만들어 회계 담당자에게 SMTP로 직접 보낸다. 운행기록부 시트에 "검토" 열(목적 미확정·운전자 미확정·거리 미확정·증빙 없음·중복 영수증)이 있고, 검토 시트에 해소 방법이 적혀 있다. 검토 항목은 **운전자가 차 안에서** 해소하고, 다음 생성에 반영된다.

이 구조의 이유는 셋이다. ① **서버가 죽어도 기록·엑셀·메일이 된다** — 세무 자료가 외부 서비스 가용성에 묶이지 않는다. ② **운행 데이터가 서버에 없다** — 운전자 이동 정보의 유출 면적이 최소다. ③ 서버는 영수증 중계와 기준 정보 배포만 하므로 **작고 바꾸기 쉽다**. 다차량 합산이 필요해지면 운행 사본을 올리는 경로 하나를 추가하면 된다(10.7 로드맵).

## 4. Pleos SDK·API 활용 계획

Pleos Connect SDK는 Kotlin으로 작성된 Android 라이브러리로 Java·Kotlin 앱 모두에서 호출할 수 있다(공식 문서가 두 언어 예제를 제공). AutoLog는 SDK·공식 샘플과 같은 Kotlin으로 차량 앱을 작성하고, 백엔드도 Kotlin(Spring Boot)으로 통일한다. 아래는 Pleos Connect SDK(Vehicle · NaviHelper · Fused Location · Gleo AI · ADAS) 중 AutoLog가 쓰는 것과 그 역할, 통합 순서다. "핵심"은 없으면 앱이 성립하지 않는 것, "2차 통합"은 1차 핵심이 돌아간 뒤 11.15 전에 붙이는 것이다.

| SDK·API | AutoLog에서의 역할 | 통합 순서 |
|---|---|---|
| Vehicle SDK — Odometer | 계기판 누적 주행거리 → 운행거리의 유일한 출처 | **1차 핵심** |
| NaviHelper SDK | 내비 목적지·경로 상태 → 도착지 라벨, 도착 판정 | **1차 핵심** |
| Fused Location SDK | 차량 GPS·IMU·카메라 융합 위치 → 출발·도착 좌표, 등록 장소 자동 매칭 | **2차 통합** |
| Gleo AI — SpeechToText | 정차 후 "판교 A고객사 미팅" 한마디로 목적·비고 입력 | **2차 통합** |
| Gleo AI — TextToSpeech | "운행 종료. 23.4 km, 거래처 방문으로 기록할까요?" 음성 안내 | 2차 통합(선택) |
| Vehicle SDK — Fuel | 연료량 급증 → 주유 이벤트 보조 감지 | 보조 |
| Vehicle SDK — CarInfo | 차량 모델·식별 정보 → 차량 자동 등록 | 보조(제공 범위 확인) |
| Vehicle SDK — DrivingMode | P/D 전환 → 정차·주행 판정 보조 | 보조(제공 범위 확인) |
| Pleos Fleet API | 다수 차량 원격 데이터 | 계약 이후 확장 |
| Vehicle Data API | 클라우드 차량 데이터 | 국내 MVP 제외(유럽 한정) |

**Fused Location을 쓰는 이유:** 스마트폰 GPS는 터널·고층 구간에서 끊기지만 Fused Location은 차량 IMU·카메라로 보정된 위치를 준다. 출발지를 "직전 도착지로 추정"하는 대신 실제 좌표로 등록 장소(본사·거래처·자택)에 매칭할 수 있어 목적 추천 정확도가 올라간다. 경로는 저장하지 않고 **출발·도착 2점만** 쓴다.

**의존성 원칙:** 핵심 흐름(거리 기록 → 목적 승인 → 장부)은 Odometer + NaviHelper만으로 완성된다. 백그라운드 콜백이 막혀도 앱 복귀 시 계기판 재조회로 거리는 복구된다. Fused Location이 없으면 출발지는 직전 도착지·사용자 선택으로, STT가 없으면 4지선다 탭으로 대체되며 앱은 멈추지 않는다. 하나의 SDK가 막혀도 전체가 서지 않는 구조다.

**검증 순서:** Pleos Playground 프로젝트 생성 → 에뮬레이터에서 Odometer 조회 → NaviHelper 콜백 수신 → Fused Location 콜백 수신 → 값 갱신 주기·단위·정밀도 확인. 1차 핵심 두 개의 결과가 나머지 자동화 범위를 결정한다.

### A. 거래처 방문 (운전자)

### B. 주유 후 비용 반영

법인카드 68,000원 결제 → 정차 중 폰으로 영수증 촬영 → OCR(40.00 L × 1,700원 = 68,000원 검산 통과) → 거래 시각으로 당일 운행·차량 매칭 → '연료비'로 장부 반영. 중복·불일치는 검토 대상으로 남긴다.

### C. 월말 마감

차 안 정차 중 [운행기록부] → 11월 → [보내기] → 수신자 체크(회계팀 김○○) → 탭. 168건 중 164건 확정, 4건이 "검토" 열에 표시(목적 미확정 2, 증빙 없음 1, 거리 미확정 1). 회계 담당자는 메일 첨부 엑셀의 검토 열을 필터해 운전자에게 확인을 요청하고, 운전자는 다음 정차 때 차 안에서 해소한다. 모든 값에 출처와 수정 이력이 남아 있다. *(수치는 UI 설명용 가상 데이터)*

## 7. 기술 아키텍처

```
[Pleos Connect 차량 앱 — Kotlin / Jetpack Compose]  ← 장부의 원본
  Vehicle SDK · NaviHelper · Fused Location · STT
  Room(운행·비용·직원·장소·배차·수신자) · Foreground Service · 목적 추천 · 검토 계산
  XLSX 생성(Apache POI) · SMTP 발송(Jakarta Mail)
          │ 서버 → 차 (inbox 수신, 단방향)        └──── SMTP ────► 회계 담당자
          ▼
[중계 서버 — Kotlin / Spring Boot + PostgreSQL + MinIO]
  기기 등록 · 영수증 수신 → Gemini OCR → 차량 inbox · 직원·장소·배차·수신자 → 조직 차량 inbox
          ▲                          ▲
   [폰: QR → 카메라 페이지]     [운영 웹(경량): 차량·직원·장소·배차·수신자]
```

| 구성 | 기술 | 이유 |
|---|---|---|
| 차량 앱 | Kotlin 2.0, Jetpack Compose, 코루틴 | Pleos SDK·공식 샘플이 Kotlin. 콜백을 코루틴으로 감싸 순차 코드로 작성 |
| 차량 연동 | Vehicle SDK 2.3.x, NaviHelper 3.0.x, Fused Location 1.0.x, Gleo AI(STT) | 거리·목적지·좌표·음성 입력 |
| 로컬 DB | Room | **운행·비용의 원본.** 오프라인 기록·복구 |
| 엑셀·메일 | Apache POI, Jakarta Mail(SMTP) — 차 안에서 | 서버 없이 회계 담당자에게 직접 전달 |
| 중계 서버 | Kotlin(JVM 17), Spring Boot 3, PostgreSQL, MinIO | 영수증 OCR 중계·기준 정보 배포만. 운행 데이터 미보관 |
| OCR | **Gemini API**(gemini-2.5-flash), 서버에서 호출 | 이미지→구조화 JSON 한 번에. 키는 서버에만 |
| 장부 | Apache POI(안드로이드) | 국세청 양식 XLSX를 차 안에서 |
| 운영 웹·카메라 페이지 | React + TypeScript / 정적 HTML 1장 | 기준 정보 5화면. 대시보드·운행 화면 없음 |
| 공용 모듈 | `shared`(Kotlin JVM) | inbox payload DTO를 앱·서버가 공유. 모노레포 |

**데이터 모델 — 차량 Room(원본):** trips, stops, expenses, users, places, schedules, recipients, reports, vehicle_state. **중계 서버:** organizations, admins, vehicles, connect_codes, inbox, receipts(30일), users/places/schedules/recipients(배포용 원본). 서버에 운행·비용 테이블은 없다.

trips 레코드 예시(내부 포맷, Pleos API 응답 아님):

```json
{
  "trip_id": "trip_001",
  "vehicle_id": "vehicle_001",
  "user_id": "user_001",
  "start_time": "2026-11-02T09:00:00+09:00",
  "end_time": "2026-11-02T09:35:00+09:00",
  "start_odometer_km": 18420.5,
  "end_odometer_km": 18443.9,
  "distance_km": 23.4,
  "destination_label": "판교 A고객사",
  "purpose_category": "BUSINESS",
  "purpose_detail": "CLIENT_VISIT",
  "purpose_source": "USER_CONFIRMED",
  "distance_source": "VEHICLE_ODOMETER",
  "status": "CONFIRMED"
}
```

`distance_source`, `purpose_source`, `status`가 "무엇이 자동이고 무엇이 승인됐는지"를 구분한다.

## 9. 경쟁 분석 및 차별화

### 9.1 기존 서비스

| 구분 | 대표 | 방식 | 한계 |
|---|---|---|---|
| 스마트폰 운행일지 | 카택스, 드라이브로그 등 | 폰 GPS, 블루투스·충전 감지, 비콘 | 폰·장치 의존, GPS 오차, 차량 밖 기록 |
| 플릿 관제 | Pleos Fleet(유럽, Geotab 협력), 렌터카·보험 계열 | 클라우드 텔레매틱스 | 대형 플릿·관리자 중심, 국내 세무·영수증 흐름 부재 |

카택스는 국내 업무용 차량관리 1위 사업자로 운행일지·유류비·관제를 통합 제공한다. "운행기록부를 자동으로 만든다"는 문장만으로는 차별화가 되지 않는다.

### 9.2 AutoLog의 위치

| 비교 | 스마트폰 운행일지 | Pleos Fleet | **AutoLog** |
|---|---|---|---|
| 거리 출처 | GPS·비콘 | 차량 텔레매틱스 | **차량 계기판(Vehicle SDK)** |
| 실행 위치 | 폰 | 클라우드·관리자 웹 | **차량 디스플레이(Pleos Connect)** |
| 운행 데이터 보관 | 사업자 서버 | 사업자 클라우드 | **차량 안(Room). 서버에 올리지 않음** |
| 공용차 운전자 | 폰 주인으로 가정 | 관제 대상 | **1탭 사용자 선택 + 배차 역추론** |
| 앱 꺼진 구간 | 기록 없음 | — | **계기판 차이로 거리 복구** |
| 운전자 역할 | 앱 실행·입력 | 없음(관제 대상) | **정차 시 1탭 승인** |
| 목적지 | GPS·수동 | — | **NaviHelper** |
| 지출 증빙 | 별도 기능 | — | **운행에 자동 연결** |
| 세무 양식 | 국세청 양식 | 해외 리포트 | **국세청 양식 + 출처·이력** |
| 타깃 | 중소 법인 | 대형 플릿(유럽) | **국내 중소 법인·개인사업자** |

**한 줄 포지셔닝:** 카택스는 폰이 기록하고, Pleos Fleet은 클라우드가 관제하며, **AutoLog는 차 안에서 운전자가 쓰는 장부**다. Pleos Fleet이 관리자의 눈이라면 AutoLog는 운전자의 손이며, 향후 Pleos Fleet API와 연동해 중소형 법인의 진입 상품이 될 수 있다.

*"카택스가 Pleos SDK를 붙이면 되지 않나"에 대한 답:* AutoLog는 그 가능성을 부정하지 않는다. 다만 차량 앱 마켓 선점, 운행–증빙 통합 데이터 모델, 현대차그룹 차량 소유자와의 직접 접점이 먼저 쌓인 쪽이 유리하며, 이것이 Pleos App Market 생태계가 만들어내는 가치다.

### 10.3 예상 MAU (가정 기반)

*아래는 검증되지 않은 내부 가설이며, 고객 인터뷰와 파일럿 데이터로 조정한다.*

**Bottom-up — 영업으로 확보하는 숫자**

| 단계 | 시점 | 가정 | MAU |
|---|---|---|---|
| 파일럿 | 출시 ~3개월 | 20개사 × 평균 5명(운전자 4 + 관리자 1) | **100** |
| 초기 확산 | 6~12개월 | 100개사 × 5명 + 개인사업자(Pro) 300명 | **800** |
| 성장 | 24개월 | 500개사 × 5명 + Pro 2,000명 | **4,500** |

**Top-down — 시장이 허용하는 상한**

| 단계 | 가정 | 산식 |
|---|---|---|
| 모수 | Pleos Connect 탑재 차량 누적 보급(2026 2Q 신차부터) | [연간 보급 추정치 입력] |
| 업무용 비중 | 법인·개인사업자 명의 약 25% | × 0.25 |
| 설치율 | 앱 마켓 노출 + 세무 니즈, 1년 차 8% | × 0.08 |
| 활성률 | 월 1회 이상 운행·장부 확인 70% | × 0.70 |

예: 모수 30만 대 → 업무용 7.5만 → 설치 6,000 → **상한 MAU 약 4,200**. Bottom-up 24개월 목표(4,500)가 이 상한과 같은 자릿수라는 점이 두 추정의 일관성 근거다. Lease·Family 모드가 붙으면 업무용 비중 제한이 풀려 모수가 커진다.

### 10.4 Retention 정의와 근거

**정의:** 해당 월에 실제 이용(운행 기록 1건 이상 또는 관리자 검토 1회 이상)이 확인된 법인·운전자 중, **다음 달에도 최소 1회 운행 또는 검토를 수행한 비율**(월간 재사용률).

| 지표 | 파일럿 목표 | 근거 |
|---|---|---|
| 월간 재사용률 | 70% | 월말 운행기록부 제출이라는 **강제 주기**가 있어 자연 재방문 발생 |
| 3개월 리텐션 | 60% | 운행·증빙·승인 이력이 쌓일수록 **전환 비용** 상승 |
| 월말 장부 다운로드율 | 80% | 사용자가 앱을 열지 않아도 기록이 쌓이고, 열면 완성된 장부가 있는 **상시 가치** |

*모두 목표치이며 측정 전이다.*

### 10.5 수익 모델

| 플랜 | 대상 | 가격(가정) | 포함 |
|---|---|---|---|
| Pro | 개인사업자 | 무료 | 운행기록·엑셀·메일 — 서버 없이 차 안에서 전부 |
| Business | 중소기업 | 차량당 월 3,000~5,000원 | OCR 중계·운영 웹·배차 |
| Fleet | 기업 | 별도 견적 | 다차량·외부 시스템 연계 |

공모전 시연 기능은 결제 없이 동작한다.

### 10.6 기대 효과(가설)

법인차 10대, 일 3건 운행, 월 20일 → 월 600건. 건당 수동 처리 2분 → AutoLog 20초. **월 20시간 → 3.3시간, 약 83% 절감.** *(운행기록 처리만 비교한 시뮬레이션, OCR 검토·초기 설정 제외)*

### 10.7 확장 로드맵

**1단계(공모전):** 차 안 원본 + 영수증 OCR 중계 + 기준 정보 배포. **2단계:** 운행 사본 업로드(`POST /trips` 하나) → 다차량 합산 엑셀, 폰에서 내 운행 조회·사후 확정, 운전자 폰 배차 예약. **3단계:** 전기차 충전비 → 주차·통행료·정비 영수증 → 법인카드 API 제휴 → Pleos Fleet API 연동 → 중고차 매각용 차량 이력 리포트. Room이 원본이라는 원칙은 3단계까지 유지되고 서버는 사본만 갖는다.

### 11.4 팀 역할 — 로직 2인 + 프론트

**화면은 프론트 담당이 따로 만든다.** 차량 앱 Compose 화면, 운영 웹, 카메라 페이지 전부. 로직 2명(앱 A·B)은 `vehicle-core/` 모듈(화면 없는 로직)과 `relay/`를 맡고 화면이 부를 인터페이스(`core/Contracts.kt`)까지 책임진다. 화면 코드는 `app/`·`web/`에 둔다. 로직은 **SDK 기준**으로 나눈다 — 차량 데이터(Vehicle SDK)와 맥락(NaviHelper·Fused Location·Gleo AI)은 서로 의존이 없어 한쪽이 막혀도 다른 쪽이 돌아간다.

| | **앱 A — 차량 데이터·기록·출력 코어** | **앱 B — 맥락·판단·중계** |
|---|---|---|
| 한 줄 | 계기판을 읽어 운행을 만들고, 절대 잃지 않고, 엑셀로 내보낸다 | 운행에 "어디로·왜·누가"를 붙이고, 폰·관리자 입력을 차로 잇고, 메일로 보낸다 |
| 담당 SDK | **Vehicle SDK** — Odometer, DrivingMode, CarInfo, Fuel | **NaviHelper, Fused Location, Gleo AI(STT·TTS)** |
| 차량 앱 로직 | 운행 상태기계, 거리 계산, Foreground Service·알림, 보존·복구·놓친 운행, 주행 중 판정, Room, 차량 연결, inbox 수신, 엑셀 생성(POI), 검토 계산 | 목적지·좌표, 목적 추천 규칙, 운전자 확정·사용자 정렬, 거래처 등록 판단, 음성 입력(목적·주유 파싱), 영수증–운행 매칭, **SMTP 메일 발송**, SMTP 계정 보관 |
| 서버 | — | **중계 서버** 전체(Spring Boot: 기기 등록·QR·Gemini OCR·inbox·배포, 운영 웹이 부를 admin API) |
| 리스크 | Odometer 정밀도·백그라운드 콜백·절전 생존·POI 빌드 → **검증 1순위** | 범위가 넓음(SDK 3종 + 서버) → STT는 막히면 버림, admin API는 2차 |

| 프론트 | 차량 앱 화면(사용자 선택, 메인 3상태, 목적 카드, 영수증 확인, 보내기, 이력, 설정, 놓친 운행 배너), 운영 웹 5화면, 카메라 페이지 |
|---|---|

세 사람이 만나는 지점은 **`core/Contracts.kt`** 하나다(기술명세 8장). 첫날 A·B가 이 파일과 fake 구현을 커밋하면 프론트는 fake로 화면을 다 만들 수 있고, A·B는 화면 없이 단위 테스트·로그로 로직을 완성한다. 11.14에 셋을 합친다.

## 12. 최종 PT 시연 구성 (약 3분)

1. **앱 실행 → 사용자 선택** — 배차된 운전자가 첫 카드에 강조, 1탭. 현재 Odometer 표시
2. **운행 시작 → 내비로 전환** — 지속 알림의 km가 갱신됨. 에뮬레이터에서 Odometer·목적지·위치 변경, 도착 좌표가 등록 거래처에 매칭
3. **정차 후 목적 승인** — '거래처 방문' 추천 → 1탭 확정, 또는 "거래처 미팅"이라고 말해 음성으로 확정. 미등록 목적지면 "거래처로 등록" 제안
4. **놓친 운행** — 앱을 닫고 Odometer를 +15 km 올린 뒤 열면 "기록되지 않은 운행 15 km" 배너 (영상 대체 가능)
5. **영수증 등록** — 차에서 [영수증 저장] QR → 폰으로 촬영 → 15초 뒤 차 화면에 OCR 카드 → 1탭 확정
6. **운행기록부 완성** — 차에서 [운행기록부] → [보내기] → 메일 도착 → 엑셀 열기: 운행·비용이 한 줄, "검토" 열, 검토 시트. **"서버를 꺼도 이 장면은 됩니다"**

에뮬레이터 값과 실제 차량 검증 여부를 화면에 명시한다. 검증하지 않은 기능을 검증한 것처럼 설명하지 않는다.

### 12.1 선택 제출물(가산점) 계획 — 11.15 전 확정

접수양식 7번(참고자료)은 선택이지만 가산점이 있다. 아래 세 가지를 제출 가능한 상태로 만든다.

| 제출물 | 11.15까지 목표 수준 | 담당 |
|---|---|---|
| GitHub 저장소 | public 모노레포, README에 아키텍처·SDK 검증 결과(`vehicle-core/docs/sdk-findings.md`)·빌드 방법. 차량 앱은 Odometer·NaviHelper·Fused Location 콜백 수신 + 백그라운드 기록까지 동작 | 앱 A |
| 시연 영상(2~3분) | 사용자 선택 → 운행 시작 → 내비 전환·알림 갱신 → 정차 후 목적 승인 → QR 영수증 → 차 화면 OCR 카드 → 차에서 메일 발송 → 엑셀 검토 열. 에뮬레이터 입력값임을 자막으로 명시 | PM |
| APK | 차량 앱 debug APK. 서버 미연결 상태에서도 사용자 선택·로컬 기록·승인 UI가 도는 빌드 | 앱 A |
| 화면 시안 | 차량 ProfilePicker·Home·ReviewTrip, 엑셀 양식 1장 | 프론트(화면)·앱 A(엑셀) |

저장소·영상·시안에 팀원 실명·연락처·계정 정보가 노출되지 않도록 제출 전 확인한다. 미완성 링크나 개발 성과를 임의로 적지 않는다.

## 14. 개인정보·안전

| 영역 | 원칙 |
|---|---|
| 수집 최소화 | 운행·비용 처리에 필요한 데이터만. 상세 경로는 MVP 제외. **운행 데이터는 서버에 올리지 않고 차량 안에만 보관** |
| 영수증 | 서버 보관 30일 후 자동 삭제. 카드번호 뒷 4자리만 |

| 보안 | 전송 TLS, 저장 암호화. 영수증 카드번호는 **뒷 4자리만** 저장, 전체 번호는 어디에도 두지 않음 |
| 감사 로그 | 조회·수정 이력 기록 |
| 퇴사·탈퇴 | 권한 회수와 법정 보존 데이터 분리 |
| 운전자 주의 | 주행 중 입력 UI 미노출, 내비 미가림 |

법인 차량이라도 운전자 이동 정보를 무제한 수집·열람할 수 없다. 배포 시 개인정보보호법·위치정보법·근로자 정보 처리 요건을 별도 검토한다.

## 16. 접수양식 매핑 (제출용 압축 가이드)

공식 접수양식("02 앱 프로젝트 소개 / 심사 자료")이 곧 기획서다. 분량 제한은 없지만 심사위원은 양식 순서로 읽으므로, 이 문서의 내용을 아래처럼 8칸에 배분한다. 각 칸의 첫 문장이 심사 기준 중 무엇에 답하는지 드러나게 쓴다.

| 양식 항목 | 이 문서에서 가져올 내용 | 분량 가이드 | 주로 답하는 심사 기준 |
|---|---|---|---|
| 1. 한 줄 소개 | 표지 한 줄 소개 + 슬로건 "운전만 하세요. 기록은 차가 합니다." | 1~2문장 | 차량특화성 |
| 2. 기획 배경 | 1장(문제 정의: 검증·정산 수작업, 공용차 귀속) + 9.1(기존 서비스가 해결한 것과 남은 틈) + 10.1 초기 타깃 | 3단락 | 창의성(Pain Point 정의), 사업성 |
| 3. 주요 기능 및 차량 특화 요소 | 2.2 설계 원칙 4개 + 3장 기능 요약(사용자 선택·백그라운드 기록·놓친 운행 복구 포함) + 6장 UI 원칙 + 9.2 한 줄 포지셔닝 | 기능당 2~3문장 | 차량특화성, 창의성 |
| 4. 주요 사용 시나리오 | 5장 A·B·C 그대로 | 시나리오당 1단락 | 차량특화성 |
| 5. 개발 계획 | 4장 SDK 표(1차 핵심/2차 통합/보조) + 7장 아키텍처 요약 + 11.3 일정 + 15장 리스크·대체안 | 4블록 | **기술 활용성** |
| 6. 기대효과 및 발전 가능성 | 10.3 MAU(bottom-up + top-down) + 10.4 Retention 정의 + 10.6 기대 효과 + 10.2 모드 확장 + 10.7 로드맵 | 4블록 | **사업성** |
| 7. 참고자료(가산점) | 12.1 제출물 계획의 실제 링크 | 링크 + 1줄 설명 | — |
| 8. 숏폼 링크 | 선택. 영상 게시 시에만 | — | — |

**양식에 넣지 않는 것:** 7장 DB 스키마·JSON, 8장 예외 처리 표 전체, 13장 정량 목표 표 전체. 이들은 별지 또는 GitHub README로 뺀다. 양식 안에서는 "원본값·출처·수정 이력을 저장한다", "Odometer 조회 실패 시 추정값으로 채우지 않는다" 같은 **원칙 문장**만 남긴다.
